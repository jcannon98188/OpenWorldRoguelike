# Embeddable script runtimes for .NET with a hard sandbox

Research for #20 (part of map #1). Researched 2026-10-18. Every claim cites its owning source; items I could not confirm are marked **Unverified**.

Scope note: `docs/adr/0014-*` and `0015-*` do not exist on `main` at the time of writing (only 0001 and 0002). The constraints below are taken from issue #20 and ADR-0001: a script-backed Part must be indistinguishable from a C# Part to dispatch (registered by ID, same event context, serializable state, deterministic), handlers use only the zone RNG, no wall clock, no unordered iteration, and simulation state is integer-only (ADR-0014 as cited in the issue).

## Recommendation

Use **WebAssembly hosted in Wasmtime via `wasmtime-dotnet` (package `Wasmtime` 48.0.2)** as the Content Pack script runtime, behind a narrow `IScriptHost` seam. It is the only candidate that gives all of:

- **Capability sandbox by construction.** A guest can only do what its explicitly linked imports allow ([Wasmtime security](https://docs.wasmtime.dev/security.html)). Nothing is granted unless the host links it.
- **Deterministic CPU budgets.** Fuel gives reproducible interruption points ([Wasmtime interrupting](https://docs.wasmtime.dev/examples-interrupting-wasm.html)), exposed as `Config.WithFuelConsumption` and `Store.Fuel` ([wasmtime-dotnet source](https://github.com/bytecodealliance/wasmtime-dotnet/blob/main/src/Store.cs)).
- **Hard memory caps.** `Store.SetLimits(memorySize, tableElements, instances, tables, memories)` ([Store.cs](https://github.com/bytecodealliance/wasmtime-dotnet/blob/main/src/Store.cs)).
- **Integer determinism.** Wasm integer ops are deterministic and wrap ([Wasm spec numerics](https://github.com/WebAssembly/spec/blob/main/document/core/exec/numerics.rst)); floats can be forbidden by a load-time validator (see Determinism).
- **Byte-stable script state.** A Part's state lives in linear memory, which is a byte array the host can snapshot and hash (reasoning from the Wasm model; no source quotes a snapshot API, see Open items).

The cost is authoring: modders compile to Wasm (AssemblyScript, Rust, C and similar) rather than write a script. If that cost proves too high for hobbyists, the fallback is **Lua 5.4 through NLua/KeraLua** (native), which has real integer semantics but a weaker sandbox story (see Candidates). Do not use Roslyn scripting or a collectible `AssemblyLoadContext` for untrusted packs.

## Context fit

ADR-0001: handlers run server-side, in a total deterministic order, and a script-backed Part must be dispatch-identical to a C# Part. ADR-0002: clients never run handlers, so the runtime is server-only. That removes any need for client-side script portability, and it means one native dependency on the server is acceptable. The hot path is event dispatch (Query/Before/After), so per-call overhead matters; instance reuse and batching host calls are the main levers.

## Candidates

### Wasmtime + wasmtime-dotnet (recommended)
- **Health.** `wasmtime-dotnet` is under `bytecodealliance`, Apache-2.0, not archived, last push 2026-10-16, latest release v48.0.2 (2026-09-18) ([repo API](https://api.github.com/repos/bytecodealliance/wasmtime-dotnet), [releases](https://api.github.com/repos/bytecodealliance/wasmtime-dotnet/releases)). Wasmtime itself: Apache-2.0, v49.0.3 released 2026-10-14, ~18.7k stars ([repo API](https://api.github.com/repos/bytecodealliance/wasmtime)). NuGet license is `Apache-2.0 WITH LLVM-exception`, ~2.0M downloads ([NuGet](https://www.nuget.org/packages/Wasmtime)). The binding tracks Wasmtime majors closely but lags the newest (48 vs 49).
- **.NET 11.** The csproj targets `netstandard2.1;netstandard2.0;net8.0;net10.0` ([Wasmtime.csproj](https://github.com/bytecodealliance/wasmtime-dotnet/blob/main/src/Wasmtime.csproj)); NuGet lists net8.0 and net10.0 as compatible ([NuGet](https://www.nuget.org/packages/Wasmtime)). A net11.0 app consumes the net10.0 asset by forward compatibility. .NET 11 is at 11.0.0-rc.2 (Go-live) as of 2026-10-13 ([dotnet.microsoft.com](https://dotnet.microsoft.com/en-us/download/dotnet/11.0)). Nothing states it was tested on .NET 11: **Unverified**, add a smoke test to CI on the pinned SDK. It is P/Invoke over a native library, so the pack ships platform-specific native binaries; the NuGet page does not list RIDs (**Unverified**). v34.0.2 added a Windows ARM64 binary ([releases](https://api.github.com/repos/bytecodealliance/wasmtime-dotnet/releases)).
- **No file/network/process access by default.** "The only thing a WebAssembly instance can do is what is available through interfaces it has been explicitly linked with"; Wasmtime's stated goal is running untrusted code in a sandbox; it adds guard regions, stack checks and memory zeroing, and guarantees it "won't segfault when using its public API" ([Wasmtime security](https://docs.wasmtime.dev/security.html)). Do not link WASI at all; expose only game host functions via `Linker`. The security page defines no formal threat model, and Spectre mitigations are described as partial (same page).
- **CPU budget.** Fuel (deterministic, more overhead) vs epoch interruption (about 10% slowdown per the page, wall-clock based, non-deterministic) ([Wasmtime interrupting](https://docs.wasmtime.dev/examples-interrupting-wasm.html)). Use fuel, because wall-clock interruption would break replay. `Config.WithFuelConsumption(bool)` and `Store.Fuel` exist in the binding; `SetEpochDeadline` and an epoch callback also exist ([Config.cs](https://github.com/bytecodealliance/wasmtime-dotnet/blob/main/src/Config.cs), [Store.cs](https://github.com/bytecodealliance/wasmtime-dotnet/blob/main/src/Store.cs)). Fuel budget per call becomes a pack-level contract and is itself part of the simulation (the same input must run out of fuel at the same point).
- **Memory budget.** `Store.SetLimits(memorySize: ..., tableElements: ..., instances: ..., tables: ..., memories: ...)` ([Store.cs](https://github.com/bytecodealliance/wasmtime-dotnet/blob/main/src/Store.cs)).
- **Determinism.** Wasmtime's deterministic-execution guide lists the hazards and fixes: do not expose non-deterministic imports; NaN canonicalization is available at a cost; relaxed SIMD can be run deterministically or disabled; `memory.grow`/`table.grow` can non-deterministically succeed or fail unless limited, with fixes such as a limiter that rejects growth or a validator requiring max == min; and use fuel not epochs ([Wasmtime deterministic execution](https://docs.wasmtime.dev/examples-deterministic-wasm-execution.html)). The binding exposes `WithCraneliftNaNCanonicalization`, `WithRelaxedSIMD(enable, deterministic)`, `WithWasmThreads(false)` ([Config.cs](https://github.com/bytecodealliance/wasmtime-dotnet/blob/main/src/Config.cs)). Integer ops are deterministic and wrap; `idiv` by zero and `INT_MIN / -1` are partial operations ([Wasm spec numerics](https://github.com/WebAssembly/spec/blob/main/document/core/exec/numerics.rst)); the spec's deterministic profile only produces canonical NaNs (same page). For the integer-only rule (ADR-0014), reject any module that uses `f32`/`f64` instructions at load time with a validator (for example a `wasmparser`-style opcode scan, the approach the Wasmtime guide itself suggests for growth instructions). That is a pack-load check, not something the runtime enforces by itself. **Unverified**: that Wasmtime has a built-in "no floats" switch (I found none in `Config`).
- **State serialization.** Script-owned Part state would live in linear memory (or be passed in and out of each call). Snapshotting means copying the memory bytes, which is byte-stable provided the module is deterministic and does not embed pointers into host state. The binding's memory-access API was not read; **Unverified**. Versioned Part state (ADR-0002) means each pack must carry a state schema version that the host checks.
- **Call overhead.** Each call crosses P/Invoke into native code; no benchmark was found in primary sources. **Unverified**; measure with a spike (Query/Before/After handlers at tick rate, small payloads in linear memory).
- **Authoring and debugging.** Modders write in a language that compiles to Wasm, then ship a `.wasm`. Debug info config exists (`WithDebugInfo`) but the toolchain burden (SDKs, build step, no hot reload) is the main drawback for hobbyists. Mitigation: ship a first-party SDK template and a pure-C# test harness that runs the same `.wasm` headlessly.

### NLua / KeraLua (Lua 5.4, native), runner-up
- **Health.** KeraLua: MIT, not archived, release v1.4.10 on 2026-09-12 ([repo](https://github.com/NLua/KeraLua), [commits](https://api.github.com/repos/NLua/KeraLua/commits)). NLua: MIT, latest v1.7.9 on 2026-05-01 ([releases](https://api.github.com/repos/NLua/NLua/releases/latest)). KeraLua describes itself as C# bindings of Lua 5.4 ([README](https://github.com/NLua/KeraLua)). .NET 11 compatibility not stated; the repo has solutions for net8.0 and net10.0-android ([repo listing](https://github.com/NLua/KeraLua)). **Unverified** on .NET 11.
- **Integer semantics.** Lua 5.4 has 64-bit integer and float subtypes; integer overflow wraps ([Lua 5.4 manual](https://www.lua.org/manual/5.4/manual.html), sections 2.1, 3.4.1). That is the best natural fit for ADR-0014 among the scripting languages, but floats still exist (`/` and `^` always yield floats, per the manual), so the pack linter must forbid them or the API must provide integer-only helpers.
- **Sandbox.** Standard libraries can be opened individually with `luaL_requiref`, so `io`/`os` can be left out ([Lua 5.4 manual](https://www.lua.org/manual/5.4/manual.html)). The page does not say that omitting them is sufficient. It is a deny-list-by-omission inside the host process, backed by C code; there is no capability boundary. `string.dump`/`load` of binary chunks must also be blocked (the manual describes precompiled chunks).
- **CPU budget.** `lua_sethook` with a count mask calls a hook every N VM instructions, only while executing Lua functions ([Lua 5.4 manual](https://www.lua.org/manual/5.4/manual.html)); KeraLua exposes `SetHook` ([Lua.cs](https://github.com/NLua/KeraLua/blob/main/src/Lua.cs)). Deterministic per instruction count.
- **Memory budget.** Custom allocator via `lua_newstate`/`lua_setallocf`; KeraLua exposes `new Lua(LuaAlloc, IntPtr)` and `SetAllocFunction` ([Lua.cs](https://github.com/NLua/KeraLua/blob/main/src/Lua.cs)). A counting allocator gives a hard cap. Allocation failures are deterministic if the cap is deterministic.
- **State serialization.** Not provided. Lua tables must be walked and written with a deterministic key order by our own serializer (Lua table iteration order is not guaranteed by the manual). **Unverified** in detail; design it as `pairs`-free explicit state structs.
- **Authoring.** Best of the field: plain text scripts, no build step. Debugging needs the host's own tooling.
- **Risk.** Native C in-process: a bug in Lua or our bindings is a host crash or worse. Needs per-platform native builds.

### Lua-CSharp (pure managed)
MIT, not archived, release v0.5.7 on 2026-09-26, last push 2026-10-14 ([repo API](https://api.github.com/repos/nuskey8/Lua-CSharp)). It is a Lua **5.2** interpreter with `number` mapped to `double`/`float`/`int` ([README](https://github.com/nuskey8/Lua-CSharp)), so no integer subtype. Standard libraries are opt-in via `OpenStandardLibraries()`; a `LuaPlatform` abstraction (file system, OS environment, standard I/O, time) is used by `require`, `print`, `dofile` and `os`. Count hooks measure Lua instructions but cannot interrupt a blocking C# function, and the README says hooks "cannot enforce a strict per-state memory limit" ([README](https://github.com/nuskey8/Lua-CSharp)). Targets .NET Standard 2.1+ (same page). Verdict: attractive (managed, no native dependency, no unsafe boundary) but fails the hard memory budget and the integer-only requirement as documented. Revisit if a 5.4 integer mode and a strict memory cap land. Pre-1.0 (v0.5.x).

### Jint (JavaScript)
BSD-2-Clause, v4.17.0 on 2026-10-07, last push 2026-10-18, ~4.7k stars ([repo API](https://api.github.com/repos/sebastienros/jint)); targets net472, netstandard2.0/2.1, net8.0, net10.0 ([Jint.csproj](https://github.com/sebastienros/jint/blob/main/Jint/Jint.csproj)). Has a hardened profile: `UntrustedCodeLimits` with `TimeoutInterval`, `MaxStatements`, `MemoryLimit` and result limits, with broad CLR and reflection access disabled ([README](https://github.com/sebastienros/jint)). Its own README states "Jint is an in-process interpreter, not an operating-system security boundary", that constraints are cooperative and cannot preempt arbitrary host callbacks, and recommends a least-privileged disposable process for hostile code (same page). `TimeoutInterval` is wall-clock, so only `MaxStatements` is deterministic (reasoned from option names; the README does not discuss determinism). JavaScript numbers are IEEE doubles (language semantics; the README is silent), so integer-only discipline would have to be linted; `Date` and `Math.random` must be removed (**Unverified** how Jint exposes them). Verdict: best-maintained managed option, but the documented sandbox is explicitly weaker than a capability boundary and the language is float-first.

### MoonSharp (Lua 5.2, managed)
"99% compatible with Lua 5.2", BSD-3-Clause (README); numbers are `double` (`DynValue.Number`) ([README](https://github.com/moonsharp-devs/moonsharp), [DynValue.cs](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/DataTypes/DynValue.cs)). `CoreModules` presets (`Preset_HardSandbox`, `Preset_SoftSandbox`, ...) and strong warnings against automatic CLR interop ([sandbox page](https://www.moonsharp.org/sandbox.html)). That page does not mention instruction limits, and none were found in `Script.cs` ([source](https://github.com/moonsharp-devs/moonsharp/blob/master/src/MoonSharp.Interpreter/Script.cs)); `Processor_InstructionLoop.cs` was not read, so **Unverified**. Last tagged release v2.0.0.0 was 2016-10-14, though commits continue (latest 2026-10-14) ([releases](https://api.github.com/repos/moonsharp-devs/moonsharp/releases/latest), [commits](https://api.github.com/repos/moonsharp-devs/moonsharp/commits)); the repo license shows `NOASSERTION` in the GitHub API while the README says BSD-3. Verdict: rejected (doubles, no documented CPU or memory budgets, no recent releases).

### Roslyn scripting / compiled C# (rejected)
The Roslyn scripting docs say nothing about sandboxing ([Scripting API samples](https://github.com/dotnet/roslyn/blob/main/docs/wiki/Scripting-API-Samples.md)). Code access security, the old .NET Framework mechanism, is not supported in .NET Core/5+: CAS APIs are no-ops or throw, and Microsoft warns that code relying on them "could have a security hole" ([CAS breaking change](https://learn.microsoft.com/en-us/dotnet/core/compatibility/core-libraries/5.0/code-access-security-apis-obsolete)). Compiled C# can call anything in the process (file, network, reflection, P/Invoke), and has no instruction or memory budget. Only a source/IL allowlist verifier could constrain it, which is a large security surface to own.

### Collectible AssemblyLoadContext (rejected as a sandbox)
Microsoft states "`AssemblyLoadContext` does not provide any security features. All code has full permissions of the process" and that it exists primarily for loading isolation ([AssemblyLoadContext](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.loader.assemblyloadcontext)). Unloading is cooperative and blocked by lingering references or running threads ([Unloadability](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)). Useful for unloading trusted plugins (for example hot-reloading C# Parts we ship), not for untrusted Content Packs.

### Not evaluated in depth
Other managed JS/Lua/Wasm engines exist; I did not find primary-source evidence that any beats the above on the issue's criteria, so they are out of scope here. A pure-managed Wasm interpreter would remove the native dependency but I did not research one: **Unverified** whether a maintained one with fuel and memory limits exists.

## Suggested seam

`IScriptHost` per loaded pack: `Load(packBytes, limits)` validates (no float opcodes, no growth beyond limits, imports only from the allowed set) and returns an `IScriptPart` factory. The factory instance exposes `Invoke(eventKind, EventContext) -> EffectList`, `SaveState() -> ReadOnlySpan<byte>`, `LoadState(version, bytes)`. A script-backed Part registers by ID like a C# Part (ADR-0001) and receives host calls only through a small, versioned import table (query entity value, propose Effect, draw from the zone RNG). Per-call fuel budget and memory ceiling come from pack manifest limits clamped by server policy. Everything above `IScriptHost` stays runtime-agnostic, so swapping to a Lua backend is possible if the Wasm authoring story fails.
