# Worlds are planned at creation; Zones are synthesized lazily from designer samples

Creating a world generates a finite World Plan: the Zone graph with each Zone's ZoneId, generation key, extent, biome and role, its Zone Connections, settlement sites and faction seeds. The plan is built by the same staged pipeline as Zones, with macro stages (elevation, biomes, rivers, settlement sites, roads, faction seeds, graph) on derived RNG streams (ADR-0013), so the creation seed alone reproduces it. Each node's Recipe is chosen by a data-defined rules table over its attributes (biome, role, danger, neighbours), and a designer can pin a node to a Recipe by hand. The plan is stored in the world and is immutable after creation. World size is configuration. An unbounded world planned on demand was rejected because the coarse world layer (ADR-0009) needs a complete graph and a Zone Connection needs both ends known; generating every Zone's detail at creation was rejected for creation time and disk.

A Zone's detail is generated the first time it needs to be Resident, as a pure function of the world seed and its plan node, so it does not depend on the order Zones are visited. Zones one connection from a Resident Zone are queued for background generation at low priority (prefetch depth is configuration) on the worker path used for catch-up; a crossing into a Zone still generating waits in transit (ADR-0006). A generated Zone is saved in full immediately, and the world records the generator version and content pack hash; later changes to a generator affect only Zones not yet generated. Re-deriving a baseline from the generator plus deltas was rejected because any generator or pack change would corrupt existing worlds.

A Recipe is data: it declares the Zone's extent, within the cell budget of ADR-0003, and an ordered list of named stages, each a Rust generator registered by typed ID with parameters, validated at startup. There is no generation language. A stage receives the cell grid, the plan node and its own RNG sub-stream, so adding or reordering a stage never changes another stage's output. Designers do not tune numbers; they author two inputs. A Layout is a coarse labelled drawing of what goes where in this Zone, including socket slots and markers such as Arrival Points. A Sample is a patch of cell data in the game's own terms (ADR-0004) showing a style. A synthesis stage reads a Sample's local patterns and fills each Layout region in its style, in the manner of wave function collapse, and algorithmic stages (caves, connectivity, population, loot) can run around it. A hand-authored Zone is a Recipe whose first stage loads a template.

A Layout declares socket slots: position, facing, z-levels, a kind (road, tunnel, stair, river), and a peek depth. The plan builds the Zone graph by pairing compatible slots of neighbouring nodes, so both ends are fixed before either Zone is generated, and a Recipe must produce a walkable route between each pair of its sockets. Synthesis can hit contradictions: it retries on a fixed sequence of derived sub-seeds up to N attempts, then fails loudly to a fallback Recipe. Because designers work in an editing tool and not raw files, bad Samples and Layouts are caught there by running a Recipe across many seeds and reporting its failure rate; the runtime retry is a safety net. A Zone is synthesized whole on a worker, not Chunk by Chunk, which would need a fixed Chunk order and weaken order independence; a Zone too large to synthesize is a content decision.

## Consequences

- The generator is a deterministic library with no server dependency, so the editing tool can run it for previews and seed sweeps.
- The authoring tool is a system in its own right and shares the core's cell types and data pack.
- Generation cost per Zone is bounded by its extent and Recipe, and reported when it exceeds budget.
