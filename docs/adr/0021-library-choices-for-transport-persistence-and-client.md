# Library choices: renet, sqlx on SQLite with postcard blobs, Bevy 0.20

These are the library-level choices reopened by ADR-0020, decided from the research notes `research/rust-transport`, `research/rust-persistence` and `research/bevy-fitness` (branches; findings read 2026-10-19, nothing benchmarked).

**Transport.** `renet` 2.0.0 (or its `renet2` fork) behind our own synchronous, poll-based transport trait, using netcode secure mode with host-minted tokens (unsecure mode is testing only). It is the only candidate with no async runtime, and it has an in-memory local client for the listen server. Renet channels are fixed at setup and a reliable channel that overflows disconnects, so the Zone, Peek and party streams of ADR-0010 map onto a small fixed pool of reliable-ordered channels. The protocol version and world hash travel in the connect token and the full ordered pack list is the first reliable message, so a mismatch can name the Pack (ADR-0016). `quinn` is the fallback; `laminar`, ENet bindings and a custom UDP layer are rejected. No candidate traverses NAT, so hosts port-forward.

**Persistence.** SQLite through `sqlx`, for compile-time checked queries, with offline `.sqlx` metadata so CI builds need no live database. It replaces `rusqlite`, because only one crate per build may link the native SQLite library. WAL mode, one writer, and one persistence thread that owns all database access and runs a single-threaded tokio runtime confined to the persistence crate; the core and the simulation have no async runtime (ADR-0020), and the sim talks to persistence through channels. The schema is marked with `user_version` and `application_id`. Durability is `synchronous=FULL` for character and world saves, revisited if save latency measures badly. Turso Database (beta) and libSQL were considered and rejected: the design has one writer, concurrent writes buy nothing, and `sqlx` does not target them.

**Serialization.** `postcard` for save blobs and for the wire payload behind ADR-0010's numeric type-id registry. Its format is specified and stable but positional and not self-describing, so every Part carries its own version tag and migrations (ADR-0002). Serialized state uses ordered containers only. Dense terrain arrays may be a raw fixed-layout byte array. `bincode` (development has ceased), `bitcode` (stability is a non-goal), `rkyv` (no documented schema evolution) and `wincode` are rejected.

**Client.** Bevy 0.20.0 pinned with `=` in the client crate, in step with the pinned toolchain since each Bevy release raises the minimum Rust version. Rendering uses Bevy's own `TilemapChunk` per Chunk and z-level plus a per-cell light texture. The UI starts on Bevy UI, and `bevy_egui` serves debug overlays and the content editor. There is no visual layout editor, and the `.bsn` markup format with hot reload has not shipped, so ADR-0020's "markup with hot reload" is a gap to close in the UI ticket; Slint is a fallback only after a Windows build spike. Pack assets use a custom `AssetReader` rooted at the pack cache, with `file_watcher` in development. The compile-time setup is `dynamic_linking` with the LLD linker on stable. The client crate keeps an `AGENTS.md`, the pinned migration guides and a compiling "golden examples" crate to counter stale Bevy API from AI tooling.

## Consequences

- Spikes before build: SQLite version bundled by `sqlx` includes the March 2026 WAL-reset fix, and offline `.sqlx` metadata works in CI; Chunk load time for `postcard`, raw terrain arrays and `rkyv`; `TilemapChunk` z-order at the 0.20.0 tag; whether Slint builds with Bevy 0.20 on Windows.
- Unchecked: whether upstream `renet` 2.0.0 carries the two netcode advisory fixes that `renet2` reports, and `bevy_renet` compatibility with the pinned Bevy.
- No candidate provides LAN discovery; hosts share an address.
- A tokio dependency exists, but only in the persistence crate.
